# Readiness to resume adaptor growth

The supporting framework is ready for the next bounded adaptor. New development
has an enforceable delivery contract, a source scaffold, reusable host/native
conformance, bounded agent context, generated references, and tested authoring,
inspection and handoff paths. This is readiness to grow the catalogue; it is not a
claim that every operation or optional capability has been natively qualified.

Use the [development kit](../../adaptor-development.md) as the implementation
procedure and the [extension contract](../../adaptors.md) for native interfaces.
The [installed audit](AUDIT.md) records thirteen adaptors and fifteen document
routes after complete migration and the latest growth milestones. Fourteen routes
have scoped native qualifications; Gmsh proves the kit on a new provider.

## Boundaries

- All fifteen routes have complete development bundles and pass host conformance.
  Fourteen have source-current scoped native kit receipts. The fifteenth, since moved
  to a separately installed adaptor package, was host-qualified only; no
  delivery-contract migration remains.
- Receipt freshness covers the owning package, shared implementation and fixture
  bytes. It is conservative evidence identity, not a signature, an installation
  probe, or proof about a different runtime release.
- Native acceptance covers the named serial cases. It does not qualify all
  operations, H.264, MPI, live native editing or every optional profile. Shared
  lifecycle tests cover in-flight cancellation and owned process cleanup separately.
- The product evaluations are deterministic clients and console commands. They
  establish protocol and procedure usability; no autonomous model was evaluated.
- Schema fixture conformance is deliberately bounded. New domain semantics,
  preservation/loss rules and independent physical/numerical expectations still
  require application-specific design and tests.
- The development kit is not a promise that every future application needs no
  shared extension. Add one only for a concrete requirement, keep it independent
  of application names, and prove it against another consumer when practical.

## Next adaptor procedure

1. Select one useful bounded workflow using the [current workflow roadmap](../workflow-candidates-2026-10.md)
   and the [historical candidate context](../adaptor-candidates.md).
   Confirm public APIs, current upstream release, available runtime and acceptance
   fixtures. Keep candidate, implemented and qualified states distinct.
2. Generate and review the appropriate node/document scaffold. Complete the guide,
   operation semantics, delivery bundle, executable contracts and native verifier.
3. Supply editable baseline and variant cases, meaningful invalid input, literal
   independent expectations and explicit input/output traits and losses.
4. Run the structural admission gate, host conformance, generated-reference check
   and applicable shared tests. Add tests for domain constraints and supported
   optional profiles; do not promote a hook or a stub to qualification.
5. Run fresh bounded native conformance and a public discover/author/inspect/refine
   workflow, including its intended handoff. Check human reuse of the same input.
6. Record the successful current-source receipt, commit a compact acceptance
   summary and rerun the documented admission checks before delivery. Follow the
   separate upstream-maintenance procedure for any absorbed-version change.

No further GUI redesign or speculative universal parameter/conversion language is
needed before following this procedure.
