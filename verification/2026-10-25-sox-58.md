# SoX peak headroom (`normalise`): completion review

Scope: the new `normalise` operation of the `schemaxis.sox/1` route. The `assemble` and
`conform` operations keep their plans, losses, schema branches, commands, launchers,
receipts and limitations unchanged; their earlier reviews still apply. Native runtime:
SoX 14.4.2. The official SourceForge release list was rechecked on 25 October 2026 and
still ends at 14.4.2. `https://sox.sourceforge.net/sox.html` returned HTTP 404 on that
date, so the command mapping uses the `sox.1` manual shipped in the official
`sox-14.4.2.tar.bz2` source archive. `absorbedVersion` is unchanged.

## Gap and decision

`assemble` has a manual `gain` from 0 to 4, so an author must already know how loud a
recording is to leave room for later steps. Nothing measured the recording. `normalise`
measures the peak and applies one derived gain so the loudest sample lands on an explicit
`targetPeak`, which leaves predictable headroom for recording, publishing or encoding
drafts. This is product judgement from the inspected gap, not demonstrated customer
demand. It is peak scaling in PCM16 sample units, not loudness mastering.

## Behaviour

- Fields (all required): `source` (absolute `.wav`, the conform source contract, so
  file-artifact handoff works), `targetPeak` (integer 1 to 32767, sample units, not dB)
  and `maxGain` (finite number 1 to 16, an explicit boost ceiling).
- The host measures the largest absolute sample over every channel. Gain is the exact
  fraction `targetPeak/peak`. Silence is refused (`AUDIO_SILENT_SOURCE`); a gain above
  `maxGain` is refused (`AUDIO_GAIN_LIMIT`) before SoX starts. Nothing is capped, clipped
  or retargeted. Attenuation is always allowed. One common gain keeps channel balance.
- `maxGain` is compared as an exact fraction of the parsed JSON number's shortest
  round-trip decimal, so `6.6` is 33/5. No epsilon or clamp. JSON parsing rounds a literal
  to a double first: `6.59999999999999999999999` parses to the double `6.6` and is also
  compared as 33/5 (a test pins this); a different double just below `6.6` is refused.
- Fixed command: `sox -D --single-threaded -t wav IN -t wav -e signed-integer -b 16 OUT
  vol GAIN`, with `GAIN` the fraction as a 17-significant-digit double. No authored text
  reaches the command line. Source and budgets are the `conform` ones (32 MiB, 600 s).

## Numeric boundary repair (found in review, 2026-10-25)

The first implementation compared `Fraction(targetPeak, peak)` with `Fraction(maxGain)`.
`Fraction(6.6)` is the binary float just below 33/5, so a source peak of 5 with
`targetPeak` 33 and `maxGain` 6.6 (an inclusive, ordinary case) was refused. It was
reproduced before the repair with `AUDIO_GAIN_LIMIT`. The comparison now uses
`Fraction(str(maxGain))` of the parsed JSON number. Tests cover the literal case, a
ceiling one float step below it (still refused), a larger target (still refused), seven
further decimals, a JSON literal with more digits than a double holds (below), plus an
end-to-end run and reopening. The native qualifier runs the same case on SoX.

The text must not claim more than the code does. JSON parsing rounds every written
number to a binary double before the host sees it, and this repair does not change the
parser. `6.6` is 33/5 and `6.59999999999999999999999` also parses to the double `6.6`,
so it is compared as 33/5 and a recording that needs exactly 33/5 is accepted even
though the longer literal is below 6.6. A different double just below `6.6` is refused.
A test using `json.loads` pins both outcomes. The plan's `losses`, the capabilities
text, both guidance routes and `docs/sox.md` say this.

## Independent review repair (2026-10-25)

Wording and one test only; the numeric code, the JSON parser, the bounds and the
nonfinite and boolean refusals are unchanged.

- The `maxGain` wording above replaces "the exact decimal the author wrote". Because the
  plan's `losses` text changed, native run directories made before this repair do not
  verify under the repaired source. They stay as historical records and are not edited;
  the native qualifier was run again on the repaired source.
- The discovery text for the boost example now says a peak of 20000 (exact gain 20/3)
  with a `maxGain` of 8. It had said 29491, which the 3000-peak fixture cannot reach
  within 8. A test now ties the text, the example file and the fixture together.
- The timeline text says sample time (frame `f` at `f/rate`) is unchanged and that the
  bare 44-byte output does not carry `LIST`/`INFO` metadata of the source.
- Memory bound: a genuine native output yields at most 65536 distinct (source, output)
  pairs. The verifier allows two integer outputs per source value (an exact tie) and, for a
  forged output, one fixed chunk more before it refuses: at most twice the distinct source
  values plus one chunk. The limits themselves are unchanged.
- `positiveHeadroomPCM16` and `negativeHeadroomPCM16` are computed from the overall
  absolute output peak and are conservative bounds, not separately measured polarity peaks.
- A test comparison that could not fail was removed; the exact `<= 1/2` check beside it
  remains.

## Native observations that fixed the verification rule

| Observation (SoX 14.4.2) | Rule adopted |
| --- | --- |
| All 65536 PCM16 values at 20 gain ratios up to 16 (earlier probe): worst distance from the exact rational is exactly one half sample unit, with no stderr when no sample clips. | Every output sample must be a nearest integer to `sample*targetPeak/peak`, tolerance exactly 1/2, integer arithmetic. This is tighter than the 0.5001 constant of `assemble`. |
| Exact halves (peak 10, target 5) were rounded toward positive infinity. | Not documented upstream, so either neighbour of a tie is accepted. |
| A source with `|sample| <= peak` never clips at `targetPeak <= 32767`. | Native stderr and stdout must be empty. |

## Verification (exact, host side)

After SoX returns, the host reopens the captured source and the native output with
`wave`/`struct`-level code and checks, independently of the command line: canonical
44-byte WAV with the source's rate, channels and frame count; every scalar sample as
above; output peak equals `targetPeak`; empty native streams; exact membership, plan,
capture, launcher, command, receipt, summary and result bindings. The exact gain, peak,
duration, maximum error and headroom are stored as integers or fractions; the float
`description` block is a diagnostic compared with a small tolerance. Forged output
samples, summaries, results, plans, captures, launchers, commands and extra members all
fail even with refreshed digests (host tests).

## Limits (declared)

Peak scaling only. Not loudness, RMS, EBU R128, true-peak or inter-sample peak control,
speech quality, perceived volume, content, authenticity or identity. Boosting raises
the noise floor by the same ratio; `maxGain` protects policy and cannot tell signal from
noise. A `-32768` peak always means attenuation. Samples at an exact tie may go either
way. Serial only, one SoX process, no shared framework, registry, workflow guidance,
README or generated documentation change; shared integration is for the maintainers.
