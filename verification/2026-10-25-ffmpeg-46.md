# FFmpeg fresh verification of the single-video operations — 25 October 2026

`encodeFrames`, `encodeSheet` and `encodeVideo` previously verified only retained
`decoded.rgb`, `probe.stdout`, bindings and receipts. A coherently rewritten publication
(new `video.mkv`/`video.mp4` bytes with every retained binding, receipt hash and
publication hash refreshed, while the retained decode still matched the captured
pixels) was accepted. `muxReview` already decoded the published bytes again; this
change gives the three older operations the same decision. Authored schemas, plan
bytes, encoding argv and output bytes are unchanged.

## What changed

- `verify` (standalone, and at the end of `run`) holds the published bytes and the
  captured sources once, copies them to a private temporary directory and decodes and
  probes them there with a trusted FFmpeg and its sibling ffprobe: explicit
  `executable`, stored/invocation configuration or `FFMPEG_EXECUTABLE`. Receipt and
  submission paths and `PATH` are never used. `run` resolves the same choice in the same
  order (`--executable/--ffmpeg`, stored configuration, `FFMPEG_EXECUTABLE`) through
  the shared `trusted_runtime` helper, for the three operations and `muxReview`, and
  refuses with `INTERPRETER_NOT_FOUND` before creating the output directory or starting
  any native process. The run's own verification then receives that same choice.
- The fresh argv is fixed: local files only, container demuxer forced from the declared
  codec, output-size and address-space limits, shared deadline and cancellation.
  Each stage is bound to the digest of the held bytes it opened.
- Expectations: host-decoded captured PNG frames (`encodeFrames`, `encodeSheet`) or a
  fresh native decode of the captured source video (`encodeVideo`, selected by the
  authored range). Every frame, its order and count, dimensions, codec, pixel format,
  frame rate, duration, published frame timeline, declared BT.601 tags (H.264) and the
  fidelity budget (FFV1 exact, H.264 mean RGB error 16/255) are judged; authored
  deliverables are reassessed from the fresh observation.
- Retained JSON is strict (duplicate keys, `NaN`/`Infinity`, `1e400` refused) and
  compared by exact type; `result.json` must equal the verified outcome. Retained
  readbacks must agree with the fresh observation: identically for the same FFmpeg
  build, within 1/255 mean error per frame for another build. A contradiction is
  `VERIFICATION_FAILED` with `observed.fresh: true`.
- New `fresh.py`; `review.py` is only imported for its strict-JSON, budget and fresh-tag
  helpers and is unchanged. Discovery, planning and import stay native- and
  dependency-free (checked with an isolated import).

## Limits and consequences

- Verification is no longer offline: it needs a trusted FFmpeg with ffprobe beside it
  (`INTERPRETER_NOT_FOUND` otherwise). A run that could find FFmpeg only on `PATH`
  is now refused before any output exists (see the early-trust repair below); pass
  the executable, configure it or set `FFMPEG_EXECUTABLE`.
- The captured copies are the trust anchor and are not authenticated against the
  original paths. A coherent rewrite of a capture and all evidence, or an equivalent
  re-encode inside the fidelity budget, can verify. No signed-source authenticity or
  host-offline decode is claimed.
- Legacy untagged H.264 evidence (exact untagged encode recipe in the retained command)
  verifies without tags and reports `colourTagged: false`; the recorded command is
  inert data. No genuine untagged receipt was available, so this path is tested with
  a rewritten command record only. Historical `-vsync 0` and FFV1 level-3 records
  remain accepted as retained command records.
- H.264 results within the 16/255 budget cannot be told apart from a different
  in-budget encode. FFV1 level 1 stores no checksums.
- This is one allocation's work; it counts only after independent review and
  integration acceptance.

## Early-trust repair (review 28)

Before this repair `run` took FFmpeg from the argument, `FFMPEG_EXECUTABLE` or `PATH`,
and never read stored configuration directly. The adaptor's own end-of-run verification
accepted that choice, but the public wrapper's second verification (which holds no
executable) refused a `PATH`-only runtime. The run therefore encoded, decoded fresh once
more, and then failed, leaving a published file beside a failed `result.json`.

- `run` now calls `trusted_runtime` before creating the output directory, for
  `encodeFrames`, `encodeSheet`, `encodeVideo` and `muxReview`. It resolves the
  argument or `--ffmpeg`, then stored configuration, then `FFMPEG_EXECUTABLE`, with the
  sibling `ffprobe`, exactly as `verify` does. `PATH` is never consulted. Without a
  trusted choice it raises `INTERPRETER_NOT_FOUND` before any directory, native process
  or version probe exists. The recovery text names `--executable`/`--ffmpeg`.
- A `None` executable from the location context does not shadow stored configuration:
  `location_context` drops `None` layers, and the tests below run the public entry
  point with and without an explicit executable against a stored entry.
- Unchanged: the authored schemas, plans, native argv, output bytes, the fresh
  verification and its guards, deadline and lifecycle.
- Tests (`tests/unit/test_ffmpeg_fresh.py`): `EarlyTrustTests` (host, stub runtimes on
  a temporary `PATH`, empty private configuration, no environment variable) refuses
  both the public `adaptor.run` and `_native_run` for all four operations with no
  output directory and no marker; checks explicit over stored over environment through
  both entry points; and checks `muxReview` receives the same choice. Two native cases
  use FFmpeg 9.0.2: a genuine `PATH`-only refusal for all four operations and both
  entry points, and genuine runs plus standalone verify under every precedence pair.
- Fail-before: the same tests against the previous `run` block gave 15 host failures
  (all eight `PATH`-only cases, six stored-over-environment cases and `muxReview`) and
  9 failures and 2 errors in the native pair. Results are kept privately.
- Adapted: `test_empty_native_exit_is_not_video_success` in `test_media_geospatial.py`
  patched `os.access` and passed `/bin/true`; it now supplies an `ffmpeg` and
  `ffprobe` stub pair so it still covers an empty native exit.
- Checks run for this repair: 172 related unit tests pass with and without a runtime
  (15 native skipped without); guidance audit 0 pending and 0 stale; readiness
  admission passes. Six genuine retained runs from the earlier accepted kit
  (`encodeFrames`, `encodeVideo`, deliverable and `muxReview`) verified fresh and
  read-only. The 80-run `muxReview` rerun was not repeated; `review.py` is untouched.
- Not done: `reference --check` (ffmpeg operations and modules) and
  `generate_studio_help.py --check` (2 files) remain stale until the maintainer
  regenerates them; `qualification.json` is still not re-registered.
