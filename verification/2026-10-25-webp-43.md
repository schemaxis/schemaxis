# Bounded lossy WebP: encodeLossy (2026-10-25)

Scope: an additive operation `encodeLossy` on the existing route `schemaxis.webp/1`. One captured, fully
opaque, non-interlaced 8-bit RGB/RGBA PNG becomes one lossy WebP (`image.webp`, one `VP8 ` chunk) plus
`webp-summary.json`, accepted only inside an authored mean-absolute-RGB-error budget and byte budget. The
`encodeLossless` plan, arguments, receipts and bytes are unchanged. No near-lossless, automatic quality search,
perceptual or compression-ratio claim, animation, metadata, resize or authored native flags. No qualification
receipt is registered and `upstream.json` keeps `absorbedVersion` unset.

## Practical value and decision

Lossless is right for transparency, drawings and exactness. For opaque photograph-like or gradient images it can
be many times larger than a lossy file, so a bounded lossy branch is useful, provided the loss is measured and
refused when it exceeds what the author allowed. This is a judgement from the tradeoff, not demonstrated customer
demand. The measured examples below show both directions: lossy is far smaller for a smooth gradient and larger
and less accurate for a flat colour chart, which is why quality, error and size are authored and judged, not assumed.

Decisions: quality is a required strict integer 0-100 (100 is lossy `-q 100`, not lossless); `maxMeanRGBError` is
required (a finite number 0-255; 0 is legitimate and normally refuses); `maxBytes` is optional (1-16 MiB) and, when
omitted, the plan records the global 16 MiB cap as the default. Any alpha other than 255 is refused with
`WEBP_ALPHA_UNSUPPORTED` rather than composited. An over-budget file is `DELIVERABLE_NOT_MET` (the code `ffmpeg`
already uses) with `observed.assessment` and a `recovery`, and the run is recorded `failed`, `verified: false`.

## Verification contract (lossy)

The decision is made from the actual `image.webp` bytes, never from retained claims:

1. strict RIFF framing with exactly one `VP8 ` chunk (`VP8L`, `VP8X`, `ALPH`, animation, ICC, EXIF, XMP, trailing
   bytes, scaling bits, bad tag or start code, dimensions beyond the pixel budget are refused before any native
   decode), dimensions equal to the source;
2. byte count against `maxBytes`;
3. fresh trusted `dwebp -pam` in a private directory on a copy of those bytes; the host reads the PAM strictly,
   requires equal dimensions and alpha 255 everywhere, and computes the exact integer sum of absolute differences over
   all `width x height x 3` R, G and B samples against the PNG-decoded source;
4. `Fraction(sum, samples) <= Fraction(str(maxMeanRGBError))`: exact rational arithmetic against the budget as the decimal
   authored (the shortest round-trip text of the number, so `0.3` is 3/10, not the binary double below it); repaired
   after review 24, see the repair section;
5. all inherited strict-JSON, typed-claim, hash-bound receipt, launcher, input-binding and encode-log checks, plus the
   retained summary recomputed and compared in typed form and the result record compared as a closed set of claims (every
   key but `status`; only the text of `runtime.freshDecoder` may differ, and it must be a libwebp 1.6 identity string). The literal `-q`
   vector is rebuilt from the authored quality and compared with the retained launcher.

## Limits and what is not claimed

* The mean error is against the decode of the trusted `dwebp` with its default options (dithering is off by default:
  official dwebp documentation and 1.6.0 `dwebp.c`). Only that decode is compared. It is not
  perceptual, averages away local damage and says nothing about other decoders or viewers.
* No guarantee of compression ratio: the lossy chart above is larger than its PNG. No automatic quality search.
* Verification trusts `dwebp` and still has no independent host WebP decoder. Receipts are integrity evidence, not
  signatures. A different valid VP8 encoding inside both budgets, with the retained decode, summary, result and receipt
  all rewritten to agree, verifies (exercised natively in the repair run). The claim is decoded pixels and byte count
  within budget against `dwebp`; `request.quality`, `-m` and `-alpha_q` are authored settings that are not recovered or
  authenticated from the bytes, and nothing proves the encoder history.
* Serial only; not MPI. Not native-qualified: the ImageMagick-to-WebP route and any libwebp other than 1.6.0.
* Garbage-but-decodable bitstreams are caught by the error budget, not by the framing check; a budget of 255 accepts
  any decodable picture. That is the authored meaning of the budget.
