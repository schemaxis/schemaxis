# Pandoc 53: typed PNG image hand-off into report image blocks

Date: 25 October 2026. Route `schemaxis.pandoc/1`, operation `report`. Pandoc 3.12.1 (official self-contained build),
libwebp 1.6.0 `dwebp` as the only WebP tool (no `cwebp` in the configuration).

## Scope

The route's `acceptedArtifacts` was `["text"]` (it was `[]` in the original a702 report route, so this is not a regression).
The WebP `decodeToPng` route publishes a verified `image` artifact, but a workflow could only hand a Pandoc image block
the path of the PNG by writing it literally: `{"$artifact": "decode", "index": 0}` failed with `TYPE_MISMATCH`
(kind `image`). The route now declares `["text", "image"]`. That one manifest declaration is the whole framework-facing
change: the shared workflow binding already checks the artifact kind against the consumer's accepted kinds and returns the
verified file path, and the image block already captures, validates and embeds a PNG path. No core code, adaptor source,
native mapping, Pandoc option or AST node changed; HTML, DOCX and EPUB bytes, indices (HTML 0, DOCX 1, summary 2, optional
EPUB 3), plans and the transcript semantics are untouched. No generic `file` kind is accepted and the PNG checker is
not relaxed.

Added: `examples/schemaxis/pandoc-image-artifact.json` and `-epub.json`, `tests/unit/test_pandoc_image_artifact.py`,
`tools/qualify_pandoc_image_artifact.py`, guided text in `guidance.json`, `readiness.json`, `capabilities.py`, `upstream.json`
and `docs/pandoc.md`.

## Fail before, pass after

Before the manifest change the real workflow (WebP decode, then a report whose image `source` is the decode artifact)
stopped with `TYPE_MISMATCH`, `observed.kind = image`. The new host test run against the unchanged manifest failed 12 checks
(typed hand-off, the bad-PNG checks that never got past the kind check, the declared kinds); with the change all 9 pass. The
refusals of unrelated kinds pass both ways, as they must.

## Host tests (`tests/unit/test_pandoc_image_artifact.py`)

Independent literal PNG bytes (written in the test, not through the adaptor), a fixture producer and the real planning and
capture rules. Typed RGBA and opaque PNGs reach the image block byte for byte; table, audio, `file`, archive, video, geometry
and sprite-sheet kinds are refused with `TYPE_MISMATCH` before the consumer starts; a non-PNG, a palette PNG, an
ancillary chunk, trailing bytes, a truncated PNG and an over-size panel fail closed as `INVALID_REPORT_IMAGE`; a PNG above
4 MiB is refused and not rescaled; three valid incompressible PNGs (each under 4 MiB, together over 8 MiB) stop at capture
with `REPORT_RESOURCE_LIMIT` and no native launch; the width limits still apply to a handed-over image; literal path
reports are unchanged.

## Native acceptance (`tools/qualify_pandoc_image_artifact.py`)

Real CLI runs, every dwebp and Pandoc launch through a PID/argument logging wrapper. Four cases: the 4x3 RGBA literal
(partial alpha and RGB hidden under alpha 0) and the opaque RGB swatch, each with and without `epub`. For each, the tool
itself reads the producer PNG, the captured copy, the HTML data URI, the DOCX media part and the EPUB media part and
requires them to equal the producer bytes exactly (one image of each), compares pixels with the hand-written literal (or a
direct dwebp decode for the opaque picture), the DOCX extent (40 mm, aspect ratio retained), the HTML width and alt text, and
the capture record's geometry and hash; a read-only `verify` leaves the whole tree identical in bytes and modification times.
Also covered: resume reuses everything for an unchanged workflow; replacing the source file makes both jobs run again;
captured PNG, DOCX media, EPUB media and HTML data URI each replaced by a valid different PNG with every ordinary hash
refreshed, and a producer PNG replaced after verification, are all refused (`VERIFICATION_FAILED`; each forgery is made on its
own fresh run that first verified untouched); the decode summary JSON used as an image source is refused as
`INVALID_REPORT_IMAGE` before Pandoc starts; a literal path report is unchanged.

The native acceptance was run again against the repaired allocation-51 WebP context (libwebp 1.6.0 `dwebp` decoder only,
Pandoc 3.12.1): all four cases passed, five forgeries were refused, 124 dwebp and 78 Pandoc launches were logged. The earlier
native runs used the pre-acceptance 51 text and are not cited as proof.

## Closeout repairs

- Two host assertions in `tests/unit/test_pandoc_timedtext.py` still expected the route to accept only `text`; they now expect
  exactly `text` and `image` and that `file` is refused. The accepted kinds are unchanged by this repair.
- Readiness: the workflow scope and references, the PNG source scope and the completion scope and review now describe the
  typed PNG hand-off. The two workflow-version examples are discoverable through `profiles.workflow.references` and guidance;
  they are not listed as report-route `examples` because those must be Pandoc documents, which a workflow document is not.

## Limits (not claimed)

- Producer outputs are not all accepted. The WebP route may publish a PNG up to 5 MiB, but a Pandoc image is at most 4 MiB
  (8 MiB in total); a larger decoded picture is refused, never rescaled or truncated.
- The workflow checks the artifact kind, not the field. An image reference at a field other than an image `source` is not
  detected as misplaced (it becomes that field's path text); the guidance says so.
- Table, audio and generic-file refusals are host-tested with a fixture producer; the native run exercises the real WebP
  producer only. Not tested: other image producers (ImageMagick, ffmpeg, Aseprite, Godot) feeding Pandoc.
- Source-capture trust is unsigned semantic consistency with the producing step, not signed authenticity. No Word, device,
  reading-system, accessibility or colour-management rendering was checked, and this is not EPUBCheck.
- The qualifier registers no source-current receipt and the generated schema, operation and module references and Help were
  not regenerated here (the pinned allocation-51 context makes them pending for the coordinator's later batch).
  `absorbedVersion` is unchanged. No Pandoc mapping changed, so the Pandoc 3.12.1 upstream documentation was not re-read for a mapping.
