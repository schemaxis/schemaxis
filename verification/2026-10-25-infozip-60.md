# Info-ZIP publication bundle: new adaptor (2026-10-25)

Scope: the new `infozip` adaptor, route `schemaxis.infozip/1`, operation `bundle`. It packages one to sixteen
individually selected local files under safe flat names, plus a host-written unsigned `manifest.json`, into a
stored ZIP (`bundle.zip`) with a `bundle-summary.json`. This note covers that one operation. It claims no media,
security, privacy, accessibility or compression behaviour, no signed authenticity and no human listening or
review. No qualification receipt is registered and `upstream.json` keeps `absorbedVersion` unset: source,
registry, shared workflow guidance, generated reference and Help integration, and the receipt registration, are
master work after independent review.

## Practical value and decision

Captions, transcripts, audio and report assets are verified one at a time today, so a single verified package is a
convenient handoff. This is a product judgement from inspecting the adaptors, not demonstrated demand. It is
distinct from the core storage preservation action (`docs/storage-management.md`,
`src/schemaxis/storage_management.py`), which exports whole cases (authored input, evidence, logs, schema and history
stores) for restore. `bundle` packages only the files the author lists, under chosen names, and never adds run
directories, receipts or logs; leaving them out is a scope choice, not privacy sanitisation. No existing workflow
operation bundles selected publication bytes, so no alternative allocation was needed.

## Native mapping

* Info-ZIP Zip 3.0 is the latest 3.x release on the official pages, re-read 2026-10-25:
  <https://infozip.sourceforge.net/Zip.html> (private copy SHA-256
  `4a8908959bde1bf17e8e9d598d708ce97e995c271d2a19a7f8675bd7ebb4b6c1`, unchanged from the earlier inspection copy) and
  <https://sourceforge.net/projects/infozip/files/Zip%203.x%20(latest)/3.0/> (dynamic page; private copy SHA-256
  `639950366ba2fd6f310d118bfd6d143d1651de9e43a0053a6bebed5da57ff156`, which lists `zip30.tar.gz` and `zip30.zip`). The
  page states a 7 July 2008 release while the distribution's `zip -v` banner reads July 5th 2008; the adaptor
  therefore pins the version number (3.0), not the banner date. The SourceForge generic latest file is the separate
  UnZip beta, not a Zip release. The tested runtime is the distribution build `zip 3.0-15ubuntu3` at `/usr/bin/zip`
  (gcc 15.2.0, Linux); it was not rebuilt or installed, and no source signature was verified.
* Fixed argument arrays, no shell: `zip -v` and `zip -X -0 -q bundle.zip <names in authored order> manifest.json`,
  working directory `pack/` (private captures at mode 0600, mtime 315532800 = 1980-01-01 UTC), native environment
  exactly `LANG=C`, `LC_ALL=C`, `TZ=UTC`.
* Environment honesty: the Python launcher inherits its caller's environment; only those three variables reach the
  native `zip` through `execve`, so `ZIPOPT`, `UNZIPOPT`, `HOME` and `TMPDIR` are never passed (the test sets hostile
  values and the fake native records its environment). What proves the minimal environment is the product code and
  host tests: the launcher passes an explicit three-variable environment, the fake-native unit test records exactly that
  environment, and verification checks the launcher text. It is not an observation of the real `zip` process's
  environment, and the real-zip qualifier probe (`ZIPOPT` set in the CLI environment; see the repair section) is only an
  inference from a stored-byte comparison. The launcher applies per-process limits (address space 2 GiB,
  CPU 180 s, output file size, 64 open files). Kernel cgroup limits of the outer worker (4 GiB RAM, zero swap, 200% CPU,
  128 tasks) are separate and were not altered. The launcher records its pid and the argument array immediately before
  `execve`; that pid is the native `zip` (a fake-native unit test proves the recorded pid equals the pid the program
  observes). Supervisor, runner and replay processes are not the native process and are not claimed.

## Verifier design

Verification is native-free and runs no program. The host reads the complete `bundle.zip` with an independent strict
stored-ZIP physical reader (exact end record, central directory filling the space after the members, members tiling
from offset 0, canonical Zip 3.0 header values for version, flags 0, method 0, 1980 time, mode 0600, no extra field,
comment, ZIP64 or data descriptor, local and central headers agreeing, unique flat ASCII names, `manifest.json` last,
recomputed CRC-32) and the standard `zipfile` module as a second reader, and compares every member byte with the
captures retained in `pack/` and the manifest regenerated from them. Retained JSON is read strictly (duplicate keys,
non-finite numbers, BOM, depth) and compared by typed canonical form; summary, capture record, receipt, evidence
digests, result claims and the recorded native recipe (launcher text, argument array, bindings, process record, exit
code, silent logs) are regenerated or checked, never trusted or re-executed. Receipt executables are inert provenance.
The original sources are not read by verification, so it works after they move. Hostile archive fixtures are tiny:
4 GiB sizes, counts and offsets are refused by arithmetic and a test bounds allocation below 1 MiB.
Limit: a coherent rewrite of the archive and all unsigned captures and claims is a valid new archive; there is no
signature. The executable is needed only to create the archive.

## Review repair (2026-10-25)

An independent review required four changes, all made as a minimal patch with no new feature:
1. `verification.json` must be an exact `dict` holding exactly `artifacts`, `evidence`, `executables` and `runtime`
   before any semantic check; extra `signed`, `verified` or `signature` claims are refused (forgery tests, receipt
   edited after the hashes are refreshed).
2. Windows reserved device basenames followed by the dot (`con`, `prn`, `aux`, `nul`, `com1`-`com9`, `lpt1`-`lpt9`) are
   refused in both the name regular expression and the declared schema pattern, so planning and the archive reader both
   reject them; ordinary names such as `console.txt` stay valid. Focused grammar, schema and reader tests and the guide
   were extended.
3. Qualifier wording: the tool's `communicate()` read followed by a length check is a post-read output check, not a
   streaming memory bound; the recorded `argv[0]` is the normalised basename, not the executable path; the hard-coded
   "hostile ZIPOPT inherited but not passed" flag is removed and replaced by a policy statement separating the product
   minimal environment (launcher plus fake-native tests) from the outer kernel guard. The existing poison probe now uses
   `ZIPOPT=-l`; the byte comparison of the extracted member is recorded as an inference, not an environment readback. The
   edited qualifier was syntax-checked only and has not been rerun natively.
4. This note's unsupported before-and-after claim is withdrawn (above). Failure behaviour: a run that fails after the
   native stage can leave an unverified `pack/bundle.zip`, and a timeout or cancellation can leave `zip` temporary
   files under `pack/`; nothing is published or verified from them.
