# whisper.cpp allocation 59: host-only explicit caption line layout (`schemaxis.whispercpp.captions/1`)

Scope: the new separate route `schemaxis.whispercpp.captions/1` (`caption_layout.py`) of the whisper.cpp provider, with its manifest entry,
Studio guidance, readiness entry, discovery text, Studio template, examples, host tests and the FFmpeg publishing-handoff qualifier
`tools/qualify_whispercpp_caption_layout.py`. `correct/1`, `correct/2`, `correct/3`, `reviewed/1` to `reviewed/3`, the shared
`schemaxis.core.timed_text` validator, the transcription route `schemaxis.whispercpp/1`, its adaptor module, plans, results, publications, the
qualification record, whisper.cpp 1.9.5, FFmpeg 9.0.2 and the package version are unchanged and are not re-reviewed here. This is a practical
product judgement, not customer-demand evidence. An independent review is still required; no allocation is counted by this note.

## Why a separate route

Every existing caption publication puts one cue on one line, even after correction, and `maxSegmentLength` is a native segmentation target that
can change cue boundaries and is not a maximum. A layout that only changes selected spaces into line breaks, keeps every word, index and
millisecond, carries the source's declared review status unchanged and refuses impossible bounds is different semantics from all of them, so it
is a new route and document, not a loosened old one. The older routes already refuse its members (`UNKNOWN_ARGUMENT`), and a test pins that.

## What the route does

- Document: `version`, `operation: layout`, `source.path` (absolute `.json`), `sourceSha256` (required pin), `maxLineCodePoints` (8 to 80) and
  `maxLines` (1 to 3), all required and closed. Accepted sources are the machine `segments.json` and `reviewed/1`, `/2`, `/3`, read by the
  shared validator (4 MiB, 512 cues, 256 characters per cue, 32768 in total). The final path component must be a regular file (no link, device,
  directory or FIFO); the bytes are held once, the pin is checked against them, and the file is read again after the publications are written
  (`LAYOUT_SOURCE_CHANGED` if it differs or has vanished).
- Layout per cue: a break replaces one isolated ordinary space (no ordinary space next to it); fewest lines, then the smallest sum of squared line lengths, then the earliest first
  (and second) break. A cue that fits is never broken. Joining the lines with one space restores the cue text; an internal check refuses a
  result that does not (`LAYOUT_INVARIANT`; never observed and not exercised by a test). A run of two or more adjacent ordinary spaces is never broken, trimmed or
  normalised: it stays inside one unbreakable run (the shared validator permits such runs, so the route had to decide; keeping them whole keeps the
  round trip exact, and a cue that fits is always published). No-break and ideographic spaces are part of their run too. A run over the bound
  is `LAYOUT_WORD_TOO_LONG` (checked first) and a cue needing more lines is
  `LAYOUT_TOO_MANY_LINES` with `linesNeeded`; neither splits, truncates or widens. Lengths are Unicode code points.
- Work bound: at most 128 words per cue, three lines, 40 words per line, so the dynamic program is at most about 15 thousand steps per cue; a
  128-cue 239-code-point document is a tested case. The run checks the shared deadline and cancellation between cues.
- Publications: `captions.srt` (`file`, 0), `captions.vtt` (`file`, 1), `caption-layout.json` (`text`, 2). SRT payload is plain; WebVTT escapes
  `&`, `<`, `>` once per line. The closed summary carries the source version, bytes, SHA-256 and basis digest, the declared status, language,
  audio and model digests, the bounds, the policy text, per-cue index, times, original text, lines, line code-point lengths and `reflowed`, counts, and
  `humanReviewRequired: true` with accuracy, readability, accessibility, synchronization and identity all `false`. No source path is published.
  An empty reviewed/2 or reviewed/3 source gives an empty SRT, a WebVTT header and zero cues.
- Verification replays every publication from the captured bytes and the authored bounds and checks the typed authored document, plan, receipt
  (`runtime: host-only`), exact membership (a planted `.dispatch`, launcher, submission, link or subdirectory is a failure), capture binding and result.
  A coherent rewrite of captures, claims and receipt remains new consistent data, not authentication, and a test says so.

## Native handoff (publishing check, not recognition requalification)

An explicitly illustrative two-cue timed transcript (no recognition ran; its model and native digests are digests of placeholder text) is laid
out with 20 code points and three lines, and the published SRT artifact index 0 goes through one verified workflow into FFmpeg `muxReview` with an
FFV1 video of 20 frames at 10 fps and a PCM16 WAV of 32000 samples at 16000 Hz, both exactly two seconds and prepared natively from literal pixels
and samples. FFmpeg 9.0.2 (official CPU build, version checked) read the Matroska file back through separate invocations: the extracted SubRip equals
the hand-written text exactly (20 words, every line break, every time), the 20 frames equal the literal pixels, the PCM equals the literal samples,
and the fresh native verification passes. The WebVTT is parsed by an independent host parser against the same expectation, and FFmpeg's own WebVTT
demuxer, recorded only as a probe, produced the same SubRip (one demuxer reading, not a player or conformance claim). Controls: the same SRT by
literal path gives a byte-identical movie; resuming the verified workflow reused both jobs; a changed source with the old pin is
`LAYOUT_SOURCE_STALE` fresh and on resume and never reaches the movie; a new source with a new pin runs and reads back against its own literal lines; a
cue with a backslash lays out but FFmpeg review still refuses it (`UNSUPPORTED_CAPTIONS`), so the consumer restriction is not loosened. The layout ran
under a `Popen` that raises, so it launched no process.

The qualifier freezes the owned source files by hash before the run and checks the same hashes afterwards, and records every process it starts
with its argument vector, PID, parent PID and exit status. Wrapper, `timeout` and Python PIDs are distinct. Of the processes, the direct native runs
(FFmpeg or FFprobe exec'd directly) are separated from the harness replay interpreters (dispatch starts a Python replay script that changes directory
and execs the native command, so the native PID is the replay interpreter's PID); whether the native executable was observed in `/proc` is recorded
per process, and a child that finished first is listed as unobserved, never inferred. The harness-launched natives are not a minimal or private
environment: they inherit the qualifier's environment (including its `TMPDIR`) plus overrides, and their working directories are the job directories or
temporary directories created by fresh verification. The workflow scheduler's declared budget (CPUs, megabytes, one worker) is a scheduling number, not
a kernel limit; the whole worker was separately confined by a kernel control group (memory, swap, CPU and task limits) whose readings are kept apart
from the tool's own records.

An earlier attempt on the previous source, which refused every cue with adjacent spaces, is historical: its evidence belongs to those bytes and is
not claimed for this source. The final native attempt is the one run after the review repair below, under a fresh source freeze; its counts, PIDs
and readings are in the private run records, not predicted in this note.

## Mapping check made first

W3C WebVTT was fetched at https://www.w3.org/TR/webvtt1/ (HTTP 200; the page identifies itself as a Candidate Recommendation Draft of 20 May 2026): a cue
payload may not contain ` --> `, and caption cue text spans are characters other than LF, CR, `&` and `<` with HTML character references standing for code
points, so `&amp;`, `&lt;`, `&gt;` and LF between lines are valid payload text. The FFmpeg 9.0.2 documentation source kept with the runtime evidence was
read: its only `subrip` mention is in the LRC muxer and nothing there states SubRip payload rules (an early reading of mine that cited it for SRT or
Matroska was wrong and was corrected before use). The SRT payload contract therefore rests on the existing natively qualified review recipe and on the
readback above; SubRip is not claimed to have a normative standard. The consumer limits recorded in the docs are those of `review.py`.

## Review repair

An independent review found one Medium defect and one Low wording problem, both repaired without changing the shared validator, the older routes or
the framework. Cues with adjacent ordinary spaces were refused even when nothing needed to break. Now only an isolated single space is a break
opportunity, so such a run is kept whole, nothing is trimmed or normalised, and a cue that fits is always published. `LAYOUT_SPACING_UNSUPPORTED`
no longer exists. The long-run refusal now says "unbreakable run" and covers words joined by a no-break space or by adjacent spaces. The
documentation had promised no files after a failed run; a late failure (a changed source, or the final deadline check) can leave written files while
the result is failed and no `verification.json` exists. They are unverified and must not be published, verification refuses the directory, and the
prose now says so. No lifecycle behaviour was changed.

The earlier correction receipts (`correct/1`, `correct/2` partial and all, `correct/3`) were verified again by their own unchanged verifiers over the
retained receipt directories, read-only, with every file's content, size, modification time and mode compared before and after. That is a host
replay of existing illustrative receipts; no recognition, audio or human review took place and no native process was started for it.
