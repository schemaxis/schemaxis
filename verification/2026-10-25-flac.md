# FLAC publication: new adaptor (2026-10-25)

Scope: the new `flac` adaptor, route `schemaxis.flac/1`, operations `encodeLossless` and `decodePCM16`.
`encodeLossless` turns one captured PCM16 WAV into one native FLAC (`audio.flac`) plus `flac-summary.json`.
`decodePCM16` turns one captured native FLAC into one canonical 44-byte-header PCM16 WAV (`audio.wav`) plus
`flac-summary.json`. This note covers those two operations only. It claims no Ogg FLAC, 24-bit, float, lossy,
streaming or unknown-length behaviour and no qualification beyond the cases listed below. No source-bound
qualification receipt is registered and `upstream.json` keeps `absorbedVersion` unset until the shared
integration freezes.

## Practical value and decision

Speech preparation today is PCM16-WAV only (`sox conform` accepts PCM16 mono/stereo at 8-192 kHz, at most 32 MiB
and 600 s, and produces mono 16 kHz). FLAC is the usual compressed lossless recording and archive container, so
`decodePCM16` is the missing bridge into `sox conform` and whisper.cpp, and `encodeLossless` is the archive bridge
out of the PCM edit chain. This is a judgement from inspecting the existing adaptors, not demonstrated demand.
The adaptor is bounded accordingly: one source, no authored native flags, fixed compression level.

Budgets: PCM16 mono or stereo, 8000-192000 Hz, at most 600 s, and decoded PCM small enough that the canonical WAV
is at most 32 MiB (`MAX_PCM_BYTES` is 44 bytes under literal 32 MiB so every decoded WAV stays admissible to
`sox conform`). Refused: Ogg, ID3-prefixed files, other bit depths, float, unknown sample count, all-zero MD5,
lossy input, URLs, streaming and authored native flags.

## Native mapping (FLAC 1.5.0)

* Release: 1.5.0 (11 February 2025), the current release in the official changelog,
  <https://xiph.org/flac/changelog.html>, re-read 2026-10-25 (private copy SHA-256
  `abeedd4bddb155a04ec4f678cabbd0039d0c4d765907c1f895627ba8c6c5e307`).
* CLI documentation re-read the same day: <https://xiph.org/flac/documentation_tools_flac.html> (private copy
  SHA-256 `3eac1a3a8239f5fd22c2f75d4c915f0877a6d5ae885d18abd8fdd109b1046d50`). Format: RFC 9639,
  <https://www.rfc-editor.org/rfc/rfc9639.html> (text copy SHA-256
  `8906404937771aba300e1f7810534efbb8ef722a5a9970e11beaee858c966a13`). Source authenticity of the tested build was
  not verified by signature; the runtime is an isolated build outside the repository.
* Fixed encode: `flac -8 -V -s -w --no-padding --no-seektable --no-preserve-modtime --force-raw-format
  --endian=little --sign=signed --channels=N --bps=16 --sample-rate=R -o audio.flac source.pcm`. The host
  validates the WAV itself and writes the raw PCM bridge, so the native tool never parses a WAV.
* Fixed decode: `flac -d -s -w --no-preserve-modtime --force-raw-format --endian=little --sign=signed -o <out>.pcm <in>.flac`.
  No `--decode-through-errors`; no thread option (FLAC 1.5.0 `main.c` defaults to one thread, read independently).
  `flac --version` must print `flac 1.5.<patch>`.
* Probe findings that shaped the design (ad hoc probes, PIDs not retained, see the private checkpoint): native
  decode rejects a flipped MD5, an overstated sample count, trailing or truncated bytes and body or frame-header
  damage with exit 1; it ACCEPTS an understated sample count on a multi-frame file. The host therefore compares
  the decoded length with STREAMINFO itself. The encoder writes STREAMINFO plus a Vorbis comment (vendor string
  `reference libFLAC 1.5.0 20250211`, no comments) with the flags above.

## Verifier design

There is no host FLAC decoder and none is claimed. The host parses the container framing (STREAMINFO exactly once,
first, 34 bytes; 16-bit, one or two channels, 8000-192000 Hz, non-zero sample count and MD5; metadata block
framing; first-frame sync, reserved bits, CRC-8 and block-size consistency) and refuses everything else before any
native process starts. Verification **requires a trusted, separately configured `flac`** (explicit argument,
stored location `flac`, or `SCHEMAXIS_FLAC`) and is unavailable (`INTERPRETER_NOT_FOUND`) without it; it never
reports success offline and never searches PATH. It decodes a private copy of the actual published bytes in a
fresh process (resource caps, deadline, cancellation) and compares:

* encode: every decoded PCM byte against the PCM of the captured WAV, and STREAMINFO MD5, sample count and
  geometry against the same capture (exact PCM semantic identity, relative to the capture retained in the same
  publication directory; see Limits);
* decode: the decoded PCM against the published WAV payload, and its MD5 and length against STREAMINFO. This is
  internal consistency of the FLAC file. It does not certify that the recording is authentic or unaltered.

Retained JSON is read strictly (duplicate keys, non-finite numbers including `1e400`, depth and bool/int/float
type changes are faults) and compared by typed canonical form. `result.json` is compared as a closed set of
claims: an extra, missing, promoted or mistyped field (including inside `runtime`) is a verification failure;
only `status` (checked separately) and the text of `runtime.freshDecoder` (which varies with the verifying flac;
it must still be a FLAC 1.5 identity) are excluded. Receipt executables are inert provenance and are never launched.

### Honest account of this attempt

* The first attempt ended at a session limit before native acceptance was run. Three native acceptance runs in
  this attempt failed on defects in `tools/qualify_flac.py` itself (single-frame fixture used for count-mismatch
  cases, which the host first-frame check refuses before native; the missing-flac check ran inside the caller's
  location scope; the over-budget WAV is refused by the file bound as `INVALID_FLAC_SOURCE`, not `FLAC_BUDGET`;
  a workflow path filter matched the whole path). A first invocation also failed on `-I` ignoring `PYTHONPATH`.
  The adaptor behaved correctly in each; only the qualifier expectations were corrected. All failed logs are kept
  privately. `docs/flac.md` was corrected for the file-bound versus budget fault codes.
* One source change: `result_claims` is now closed (see Verifier design), answering the master's challenge; tests
  for extra, missing, mistyped and promoted fields were added to both unit files.
* The unit-test PID file for this attempt was lost and is not retained.

## Limits

* Host tests use fakes of the native boundary; only the native acceptance and the one real-gated unit test ran the
  real `flac`. Compressed-bitstream verification depends on the trusted `flac`; it is not host-independent.
* One runtime was exercised: FLAC 1.5.0 on this host (Linux, Python 3.14). Python 3.10-3.13 and other FLAC 1.5.x
  patch releases were not run.
* Encode verification proves exact PCM identity against the capture kept in the same, writable publication
  directory (`captured.wav`, `captures.json`). It is not encoder-setting authentication, because a different valid
  encoding of the same PCM with every record refreshed verifies. A writer who consistently rewrites the capture,
  the raw PCM bridge and every derived record and digest is not detected. Nothing here is an authenticity
  certificate for the recording or its producer.
* Decode certifies file consistency only, not authenticity. Metadata blocks other than STREAMINFO are dropped
  from the WAV (recorded in the summary); tags, cue sheets and pictures are not carried.
* The built-in adaptor manifests are discovered by scanning folders, so `flac` appears in discovery without a
  registry change. No source-current native qualification receipt is registered, the generated reference and Help
  were not regenerated, and there is no version bump.
