# QPDF allocation review — 24 October 2026

Scope: one bounded strengthening of the existing `schemaxis.qpdf/1` route. No application,
native mapping, supported format or schema field was added. This note covers only the change
below; it does not re-review the 17 October completion scope.

## Issue

`assembly-summary.json` is the published per-page identity map, but it named each page's
source only by authored name. The captured byte count and SHA-256 existed only in the run's
`capture.json` evidence. Two sources that rendered identically but differed in bytes therefore
published byte-identical summaries, so a later step reading the publication could not tell
which captured input a page came from.

## Change

The summary is now `schemaxis.qpdf.summary/2`: each `sources` entry also carries `bytes` and
`sha256` of the captured file. Saved verification recomputes the summary at the version the
retained summary declares. Genuine earlier `summary/1` runs still verify, in their earlier
shape, without being rewritten. An unknown version, a `summary/1` carrying digests, a
`summary/2` without digests or with a wrong digest, and a non-object summary are all
`VERIFICATION_FAILED`. Plan identity, `LOSSES`, publications, receipt shape, native commands
and the observation contract are unchanged.

## Limits

The digest identifies the captured source bytes. It is not a signature and not historical
attestation. Because the fresh native observation was not rerun for this change, a native run
that publishes `summary/2` has not been observed. Native requalification with the next QPDF and
MuPDF runtimes is the follow-up. Source page ranges would widen the authored schema and are
deferred.
