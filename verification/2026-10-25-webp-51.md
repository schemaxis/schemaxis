## Native results (new, this session; separate from earlier receipts)

Hand-written 4x3 RGBA literal (alpha 128/64/1/254, RGB 7,8,9 and 250,251,252 hidden under alpha 0) encoded by the real
`cwebp -lossless -exact`, decoded by the adaptor: every PNG sample equals the literal, read by the tool's own PAM and PNG
readers. Committed fixtures (lossless RGBA, lossless RGB, lossy gradient): PNG equals a direct `dwebp` decode. Lossy
encodes at q20 and q90: PNG equals the direct decode; distance to the original (6.4 and 2.1 mean RGB levels) is
informational only. Refusals with a real animated file (`img2webp`), a real VP8X/ALPH lossy file, truncated, trailing,
non-WebP and header-forged-oversize inputs launched no `dwebp`; a cleared alpha hint and a zeroed bitstream were refused
after at most the version and decode launches. Four tampered PNGs and a swapped captured WebP were refused with every
ordinary hash refreshed. A decoder-only CLI run and verification (no `cwebp`) succeeded; verification without a decoder
failed with `INTERPRETER_NOT_FOUND`. Removing the source after capture did not affect verification. Timeout and
cancellation were exercised (superseded: see below). Old `encodeLossless`/`encodeLossy` plans, result records and every artifact byte
equal those of the unmodified adaptor module, and legacy receipts written by it verified read-only and unchanged.
Pandoc 3.12.1 produced a verified report embedding the decoded RGBA PNG. PIDs, commands, bounds and exit codes are
retained in the private evidence record (`qualification-record.json`, `adaptor-dwebp-launches.log`); that record is not committed.

## Limits and unresolved work

- `dwebp` is the decoder oracle: semantic agreement with libwebp 1.6.0, not an independent host decoder, not source
  authenticity, and no claim that a lossy PNG equals the original picture. Another decoder may differ slightly.
- The PNG `IDAT` bytes depend on the host zlib; samples and structure do not.
- Pandoc accepts the PNG by path only; its workflow route takes no image artifact (outside this scope).
- Only serial native runs on one Linux host and one libwebp release; no MPI, other platforms or other WebP encoders.
- Demand for this direction is unproven.
- Master still owns: generated schema/reference/Help regeneration, registration of the qualifier receipt, the shared
  discovery ranking, and Pandoc image-artifact acceptance if wanted.

## Review-36 supersession (same day, same operation)

Review 36 accepted the operation with minor repairs. This section corrects the original private 51 report and earlier public counts, and records what was
re-run. The earlier native run and its two failed attempts are left unchanged as private evidence.

Superseded claims:

- The original private 51 report's "every `dwebp` the adaptor launched ... 48" overstated the record: 48 counted only launches through the logging
  wrapper. Verify-only calls, the four legacy runs and their read-only verifications, and the command-line run used the
  plain `dwebp` and have no recorded PID. No total of all launches is claimed.
- "two decoder launches per run and two in verification" understated the shared entry point: it makes six (four in the
  low-level run, which verifies once itself, plus the shared runtime's verification); a stand-alone verification makes two.
- "timeout and cancellation ended the owned process": the stall wrapper sleeps before it execs `dwebp`, so the real
  `dwebp` never started. What was shown is that the owned wrapper shell ended; real-decoder termination is not claimed.
- The retained failing-check names were wrong: `studio.add` passes; the 51 note failed `delivery.guide.link.17` (a
  directory link) and `studio.help` (stale packaged Help).

Changes: verification of a retained run whose captured WebP contradicts its alpha hint now fails with
`VERIFICATION_FAILED` (original fault in `cause`; a run keeps `WEBP_ALPHA_MISMATCH`); the VP8 upscaling bits are accepted
because libwebp 1.6.0 masks the field and ignores them (key-frame tag, start code, partition size, dimensions and
budgets are still checked); the qualifier requires `--webp`; the documentation links a fixture file instead of a directory.
The optional VP8L alpha-hint refusal is unchanged.

Re-run: focused host tests (103 run, 3 skipped without the real binaries; the three real-binary tests pass when
`SCHEMAXIS_DWEBP`/`SCHEMAXIS_WEBP` are set) and the native qualifier against the same libwebp 1.6.0 build (binary hashes
identical before and after). New: nine of the sixteen upscaling-bit values (eight toggles and the unchanged control) on a real lossy file decode through
`dwebp` and the adaptor to the same samples at the coded 96x60 size; a verify-time cleared-hint forgery with refreshed
hashes fails as `VERIFICATION_FAILED`; both stall-wrapper PIDs are gone after the timeout and the cancellation and the
exec marker was never written. Wrapper-logged `dwebp` launches: 100 (six per successful shared run, two where a decode
was refused after the version probe), 2 stall-wrapper shells, 26 direct probe processes; the unwrapped launches are not
counted.

Not done: no full unit suite, generated reference, Help or search regeneration; the generated reference and packaged Help
remain stale (`studio.help` still fails admission). Seven of the sixteen upscaling-bit values and all real-decoder
termination are untested. No human review of the output images took place, and no perceptual, device or independent
decoder claim is made.
