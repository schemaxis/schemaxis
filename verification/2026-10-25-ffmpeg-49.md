# FFmpeg repeated-frame preparation performance — 25 October 2026

Observed before the 46 repair: a 110-frame 960×320 `encodeFrames` clip in which every
frame is the same PNG took about 267 s through the whole audio/caption review workflow
(execute and verify together; not a decode benchmark). The host decoded the identical
immutable PNG bytes again for every frame, in `run`, in its own verification, in the fresh
native pass and in each later `verify`. This is a measured performance gap, not a defect
repair. Authored schemas, plans, native argv, encoder input bytes and every check are
unchanged; no input option, operation or native mapping was added.

## What changed

- `adaptor.frames` (`encodeFrames` branch only): each distinct held PNG is decoded and
  composited over black once per call. The table is keyed by the held bytes themselves
  (a dict lookup is a full byte comparison, so there is no digest-collision case and no
  path, size or timestamp key) and holds the matted RGB frame, not the RGBA decode, so a
  repeated frame shares one immutable buffer and no second copy exists. The table is a
  local of the call: it never crosses `run`, `verify`, the fresh native pass or a
  document. A bytearray payload is copied to bytes before it is used as a key.
- The RGBA-over-black arithmetic moved unchanged into `matte`; `encodeSheet` keeps its
  decode-once-then-matte-per-frame flow and calls the same function.
- Per frame, in order: decode (only for bytes not yet seen), the equal-dimension check, the
  `(n+1)·w·h·4` decoded-frame budget (hits count like any frame), then the first-bad-source
  refusal. Invalid bytes are never stored, so the first bad PNG still raises at its own
  position; the final 192 MiB RGB bound and the H.264 even-dimension rule run as before.
  Source capture, the byte budgets, hashing and the retained `input-NNNN` copies in
  `read_sources`, and `fresh.py`/`review.py`, are not touched.
- Peak memory falls because all RGBA decodes are no longer held until the end of the call.

## Limits

- The 267 s figure covers the whole workflow, including encoding, native decoding, audio
  and caption steps this change does not touch; only the host frame preparation shrank,
  so the workflow as a whole is expected to improve by less than the 40× of the isolated
  subset, and no whole-workflow time was re-measured after a fresh execute (the 80-run
  `muxReview` rerun and a full fresh workflow execution were not repeated).
- Reuse requires byte-identical PNGs; PNGs with equal pixels but different bytes are decoded
  separately. Nothing is shared between the run, its verification, the fresh pass and a later
  `verify`, so each still decodes every distinct PNG once. `encodeSheet`, `encodeVideo`
  and `muxReview` are unchanged.
- Timings are one machine under light shared load and are not portable.
- The 48 AAC `extractAudio` work is in another checkout based on the pre-46 repair; this
  patch touches only the `frames`/`matte` functions of `adaptor.py`, so master can merge it
  with the 48 bindings later.
- Not run: full unit suite, the 80-run `muxReview` rerun, generators, registration;
  `qualification.json` is not re-registered and `absorbedVersion` is unchanged.
