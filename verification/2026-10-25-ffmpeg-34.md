# FFmpeg H.264 readback strengthening

Scope: existing `encodeFrames`, `encodeSheet` and `encodeVideo` operations in
`schemaxis.ffmpeg/1`; no new operation, option, codec, flag or version. Review date:
25 October 2026. This is a fresh qualification on an exact FFmpeg 9.0.2 build **with
libx264**, not a new absorbed version, and the adaptor's recorded qualification
bundle has not been re-registered here.

## Runtime

- FFmpeg 9.0.2 built from the official release archive (signature verified), static,
  GPL, no assembly and no network protocols, with static libx264 from the official
  VideoLAN repository's `stable` branch at commit `b35605a` (x264 publishes no release
  versions). FFprobe sits beside FFmpeg.
- Earlier native qualification used a minimal build; this one exercises the real
  encoder, decoder, MP4 and Matroska paths used by H.264 delivery.

## Baseline: no fault in the existing recipes

`tools/qualify_ffmpeg_deliverable.py` and `tools/qualify_ffmpeg_video.py` both
completed on this runtime before any change (two H.264/FFV1 deliverables, nine FFV1
shapes, six source workflows, two 72-frame clips, all selected frames compared).
Further direct probes found no fault in: 601-frame and 600-frame H.264 and FFV1
sources, empty/text/mislabelled containers, default B-frame x264 sources, Baseline/
Main profile sources, the adaptor's own H.264 output used as a source, odd-dimension
FFV1 sources, and rejection of a high-frequency PNG that exceeds the 16/255 bound.

## Faults reproduced, then repaired

1. **Undeclared H.264 colour.** H.264 output carried no `color_space` or
   `color_range`. Verification passed because FFmpeg decodes untagged video as
   BT.601, but a player that assumes BT.709 for untagged high-definition video
   reads different colours: on a 640×360 saturated and gradient pattern the mean RGB
   error was 7.4/255 (maximum 53) against 1.5 (maximum 34) read as BT.601; on the
   32×24 solid-colour deliverable 9.7 against 1.3.
   Repair: the fixed H.264 recipe adds `-colorspace smpte170m -color_range tv`, the
   conversion FFmpeg already applied. Decoded pixels are byte-identical to the
   untagged encode; the native probe must now report both fields or verification
   fails. Offline verification still accepts the exact earlier untagged recipe for
   retained runs. FFV1 is unchanged (`bgr0`, full range).
2. **Damaged sources accepted as shorter clips.** A source whose tail was truncated
   ("partial file", "File ended prematurely", invalid NAL units) was probed and
   decoded with exit status 0 and published as a verified, shorter source; byte
   corruption in MP4 and Matroska surfaced as a misleading timestamp fault. FFmpeg's
   `stderr` already described the damage.
   Repair: any diagnostic text from the bound source probe or decode is now
   `INVALID_RESOURCE` at `$.nodes[0].options.file`, with `observed.stage`,
   bounded `observed.diagnostics` and recovery text, before frames are trusted.
   No passing recipe produced source diagnostics.

## Native limits found

- An MP4 FFprobe cannot open at all (no `moov` atom) remains `RUNNER_FAILED` with
  FFprobe's stderr retained, because a failing runtime and an unreadable source are
  indistinguishable from the exit status. This is existing, tested behaviour.
- FFV1 level 1 stores no checksums. A corrupted payload that FFmpeg decodes without
  an error is accepted and decodes to different pixels; the evidence proves what the
  file decodes to, not that it is undamaged. Recorded in the qualification receipt.
- Colour is declared, not managed: players that ignore tags, HDR and other matrices
  remain outside the contract. Profile (High) and pixel format are asserted by
  qualification, not enforced by the adaptor.
