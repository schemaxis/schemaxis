# Lossless WebP publication: new adaptor (2026-10-25)

Scope: the new `webp` adaptor, route `schemaxis.webp/1`, operation `encodeLossless`. One captured
non-interlaced 8-bit RGB/RGBA PNG becomes one lossless WebP (`image.webp`) plus `webp-summary.json`. This
note covers that route only. It claims no other WebP behaviour (lossy, near-lossless, animated, ICC,
metadata, resize) and no qualification beyond the cases listed below. No source-bound qualification
receipt is registered and `upstream.json` keeps `absorbedVersion` unset until the shared integration freezes.

## Practical value and decision

The existing image adaptors publish PNG or JPEG but no declared lossless WebP. Reusing illustrations and
transparent assets on web pages is a plausible use. This is a judgement from inspecting the existing
adaptors, not demonstrated customer demand. The adaptor is bounded accordingly: one source, no authored
native flags, fixed lossless effort.

## Native mapping (libwebp 1.6.0)

* Release: 1.6.0 is the newest of the 25 source archives in the official release index at
  <https://storage.googleapis.com/downloads.webmproject.org/releases/webp/index.html> (checked 2026-10-25).
  Tools were built from the official `libwebp-1.6.0.tar.gz` (SHA-256
  `e4ab7009bf0629fd11982d4c2aa83964cf244cffba7347ecd39019a9e38c4564`, static, no libpng). Source authenticity
  was not verified by signature.
* CLI documentation re-read on the same date: <https://developers.google.com/speed/webp/docs/cwebp>
  (`-lossless`; `-exact` preserves RGB in transparent areas, default off; `-z` lossless level, 6 a good
  default; metadata not copied by default) and <https://developers.google.com/speed/webp/docs/dwebp>
  (`-pam` retains alpha). Container and bitstream:
  <https://developers.google.com/speed/webp/docs/riff_container>,
  <https://developers.google.com/speed/webp/docs/webp_lossless_bitstream_specification>.
* Mapped commands: `cwebp -lossless -exact -z 6 source.pam -o image.webp` and
  `dwebp image.webp -pam -o reopened.pam`. Because the build has no libpng the host writes a canonical
  `P7 RGB_ALPHA` PAM bridge. `cwebp -version` prints `1.6.0` and a libsharpyuv line; `dwebp -version` prints `1.6.0`.
  Both are pinned to 1.6.x.

## Verifier design

There is no independent host WebP decoder. The host checks strict RIFF/VP8L framing (exactly one `VP8L`
chunk; lossy, extended, ICC, EXIF, XMP, animated and trailing bytes refused) and reads PAM strictly, but
only libwebp can decode the lossless data. Verification therefore **requires the trusted, separately
configured `dwebp`** (explicit argument, stored location `dwebp`, or `SCHEMAXIS_DWEBP`) and is unavailable
(`INTERPRETER_NOT_FOUND`) without it; it never reports success offline. It decodes a private copy of the
actual published bytes in a fresh process and compares every RGBA byte with the PNG decoded by the shared
bounded decoder. The receipt's recorded executable paths are inert; a trap test confirms a receipt-named
program is never launched. The shared conformance harness verifies outside the run's option scope, so it
needs the stored `dwebp` location (the acceptance tool supplies a private configuration file).

## Boundary repair after independent review (2026-10-25)

Scope: strictness and recovery boundaries of the same route. No redesign: the source frame, pixel comparison,
native commands and limits are unchanged.

| Finding | Repair | Evidence |
| --- | --- | --- |
| Retained JSON read loosely | `read_json`/`strict_json` decode UTF-8 and refuse duplicate keys, `NaN`/`Infinity`, numbers that overflow to infinity (`1e400`) and excess depth. `same_json` compares plan, capture record, summary, native input bindings and the result record's stable claims by typed canonical form, so `true` is not `1` and `66` is not `66.0`. | 11 of 11 reproduced variants were accepted before the change and refused after, with a real libwebp run (the claims are those named in the host and native tests). |
| `--dwebp` documented for bare `verify` | Help, readiness recovery, guidance, capability requirement and guide now say `--dwebp` applies to `run`; `schemaxis verify OUTPUT` takes `SCHEMAXIS_DWEBP` or a stored `dwebp` location. A run needs `cwebp` and `dwebp`; verification only `dwebp`. | Documented commands run as real CLI processes: environment route and stored-location route verified; with neither configured, `INTERPRETER_NOT_FOUND` is reported; `--dwebp` on `verify` is rejected by the parser (exit 2). |
| Tests leaked stored decoder settings | Missing-decoder tests use a private empty `SCHEMAXIS_CONFIG` and cleared `SCHEMAXIS_WEBP`/`SCHEMAXIS_DWEBP` (`location_context(None)` does not clear stored settings). A simulated stored `dwebp` configuration is also exercised. | Host tests. |
| Corrupt well-framed payload | Only the fresh `decode` launch maps `NATIVE_EXECUTION_FAILED` to `VERIFICATION_FAILED`, keeping the original fault as `cause`. Unavailable, wrong-version, timeout and cancellation faults keep their codes; a run-stage decode failure stays an execution failure. | Real libwebp: first 25 bytes, RIFF size and chunk size valid, remainder zeroed: `dwebp` exits 1 (`BITSTREAM_ERROR`), verification fails with that cause. |
| Second read of `image.webp` | The pixel-related set (captured.png, source.pam, image.webp, reopened.pam and webp-summary.json) is held from one read for the semantic decision. The image digest and decode-input binding use that same held WebP snapshot; other provenance files may be read again for their hashes. | A test counts reads (one) and flips the file between reads. |
| Directory created during start | `FileExistsError` from `mkdir` is `OUTPUT_EXISTS`. | Host test. |
| Wording | Summary rewrite is claimed only where the forged file could be summarised; first-person wording removed. | This note and `docs/webp.md`. |

A consequence of the result-record check: an equivalent re-encode (same pixels, different byte count) is now accepted only
when the forger also rewrites the result record's byte count; the stale-summary and stale-result cases were each refused
in the native run.

Verification reads one snapshot of the directory during the call. It makes no claim about a writer that changes the
directory after the call returns.

## Not claimed

No independent host WebP decoder; no signature verification of the libwebp source; no other libwebp
release; no ImageMagick-to-WebP native run (ImageMagick was not available, so that example is host-planned
only); no MPI, lossy, animated, ICC or metadata support; no colour-managed appearance claim; the encoder
command is not proven for bytes that pass the pixel check (any valid lossless encoding of the same pixels
is equivalent); the host PNG decoder's worst-case time at the pixel limit with Paeth-filtered data was not
measured.
