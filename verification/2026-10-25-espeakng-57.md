# eSpeak NG narration: explicitly selected voices (2026-10-25)

Scope: the existing `espeakng` adaptor, route `schemaxis.espeakng/1`, operation `narrate`. It gains one OPTIONAL authored
`voice` with the closed values `en-us`, `en-gb`, `fr-fr` and `es`. Everything else (plain UTF-8 text profile, rate, pitch
50, amplitude 100, budgets, synthetic-DRAFT status) is unchanged. The output is a synthetic DRAFT: no human review is
invented, and nothing is certified about pronunciation, language or accent accuracy, translation, intelligibility,
recognition, listening quality or the original speaker. No qualification receipt is registered and `upstream.json` keeps
`absorbedVersion` at 1.52.0.

## Product judgement

Fixed `en-us` made the narration draft unusable for French or Spanish scripts and for British English. Three further voices
are a small, bounded step toward reusable publishing drafts. This is a product judgement, not customer-demand evidence. There
is no arbitrary voice identifier, path, variant, phoneme or SSML input, no language detection and no translation.

## Behaviour

* Absent `voice` is exactly the old en-us narration: plan, launchers, captured record, summary (including its review
  wording), result, receipt and data fingerprint keep their bytes. An explicit `en-us` is kept as an explicit choice (it
  is never silently dropped): same sound, stages and fingerprint, with a conditional `voice` claim and the voice-specific
  review wording.
* Fixed stages per voice: `--voices=<language>` (`en`, `en-gb`, `fr-fr`, `es`) and a fixed `-v` value: `en-us` for the default and the explicit `en-us`, and the voice-file
  identifier `gmw/en`, `roa/fr` or `roa/es` for `en-gb`, `fr-fr` and `es` (see the lookup repair below; the mapping is host code, never authored). The listing must contain
  exactly one row whose first column is the selected language, with the expected name and voice file
  (`English_(America)` gmw/en-US, `English_(Great_Britain)` gmw/en, `French_(France)` roa/fr, `Spanish_(Spain)` roa/es). The
  Other Languages column and variants never select a voice, a voice listed more than once (identical or conflicting rows) is refused with its own
  message, and a runtime that does not list the voice is refused even though eSpeak NG would still speak.
* Fingerprint of CHOSEN native files, not every file the runtime may read: the four phoneme tables, the voice's own dictionary
  (`fr_dict`, `es_dict`, `en_dict`), `en_dict` (consulted by non-English voices) and the voice file. Paths stay inside the
  runtime's announced data directory. For `en-gb`, `fr-fr` and `es` the selected voice file is also read once (regular file, no symlink,
  within the 4 MiB limit), its first `language` line must be exactly the listed language (so its dictionary stem is `en`, `fr` or `es`),
  a `dictionary` line may only repeat that stem, and those same bytes are hashed; a `voices/` file shadowing the identifier is refused. It checks
  only these two attributes after `LoadVoice`/`fgets_strip` of 1.52.0 and refuses what it cannot decide; it is not a parser of all voice
  options and not a guarantee about all native data. The legacy `en-us` voice keeps its original six-file fingerprint and its voice file is hashed, not parsed.
* Every run and every verification re-synthesises every PCM byte with the trusted runtime and the same selected voice.
  The voice claim must agree across the authored document, plan, captured record, summary, receipt, result and retained
  launchers.
* The listed language label is what was requested from the runtime listing; it does not certify the accent heard.

## Review repair (care57-review-repair, 2026-10-25; same allocation, no new scope)

An independent review confirmed two Low gaps; both are repaired and the earlier evidence above is unchanged history.

* F1, duplicate listing rows: `check_voice` accepted any number of identical matching rows. It now refuses `len(rows) > 1` (identical or
  conflicting) with a distinct `UNSUPPORTED_RUNTIME` message at location `voices`; the no-row and wrong-row refusals are unchanged. The
  old test that expected acceptance of an identical repeat was reversed (also the one in `test_espeakng.py` for `en-us`, the only legacy
  behaviour that changes: a repeated `en-us` row, which real 1.52.0 never lists). Before/after: the unedited adaptor accepted an identical
  duplicate `es` row (small repro, private evidence); the new tests failed 173 times on it and pass now.
* F2, voice-file resolution check: the decision recorded before the code required it and the first implementation only hashed a fixed table. The check
  described under Behaviour was added after reading `LoadVoice`, `fgets_strip` and `LookupMnem` in the retained official 1.52.0 source (source archive
  hash recorded privately; `voices.c` and the installed files read). The three installed voice files equal the retained official-tag hashes, have first
  languages `en-gb`, `fr-fr`, `es` and no `dictionary` line. Tests use those exact bytes and cover valid forms (comments, CRLF, tabs, indented lines,
  secondary languages, a repeated expected dictionary), a wrong primary language, a right stem with another region, a missing primary language, a foreign
  or argument-less `dictionary`, malformed, over-long and non-UTF-8 content, NUL bytes, symlink, directory, FIFO, missing and over-size files (exactly the
  limit accepted, one byte over refused), a shadowing `voices/` file, single-read inspected-equals-hashed bytes, the unchanged original six-file `en-us`
  fingerprint and a broken legacy voice file not affecting `en-us` or an absent voice.
* Verification after the repair (this session, serial, private `TMPDIR`s): `test_espeakng_voices.py` 48 tests OK (1 native test skipped without a
  runtime); `test_espeakng.py` plus `test_espeakng_native_boundary.py` 60 OK (1 skipped); the two real-runtime tests (`SCHEMAXIS_ESPEAKNG` set to the
  trusted `espeak-ng`) OK; a fresh native qualifier run of the unchanged `tools/qualify_espeakng_voices.py` with the real eSpeak NG, SoX and FLAC
  passed (all voices, unknown-name and trimmed-data controls, forgeries, the French public three-step and Spanish three-step workflows); every PCM,
  fingerprint and FLAC value equals the earlier qualifier. The source files did not change during that run (hash freeze before equals after). The

## Lookup repair (care57-lookup-repair, 2026-10-25; same allocation, no new scope)

A second independent review found one further Low gap (F3); F1 and F2 above stay closed.

* F3, native voice lookup: the adaptor named the new voices by language name (`-vfr-fr`) while recording the file the listing maps them to. Reading
  `SetVoiceByName` and `LoadVoice` in the 1.52.0 source (`voices.c`, hash recorded privately) shows that a name is tried as `voices/<name>` and
  `lang/<name>`, then matched to voice names and identifier endings. If that fails, the CLI calls `SetVoiceByProperties` to select by a language score that includes the
  *Other Languages* column. So with modified data that still reports 1.52.0 the synthesis could use a file that was neither inspected nor hashed, and a fresh
  re-synthesis on the same data would agree with it. The earlier name/file PCM controls only showed the layout of the genuine installation.
* Repair: the new voices now use the fixed identifier of the voice file the exact listing names, `-vgmw/en`, `-vroa/fr` and `-vroa/es`, which the source
  resolves to `voices/<identifier>` and then `lang/<identifier>`, the file that is inspected and hashed. The profile mapping is in host code; the authored
  closed enum is unchanged and no path or identifier is authored. The legacy `en-us` (explicit or absent) keeps `-ven-us`; stages, plans (apart from the
  argument), launchers, fingerprint, summary and claims are otherwise as before, and no version was changed. The exact listing, exactly once, stays as a
  consistency check, and the *Other Languages* column never chooses a profile.
* Native check (real eSpeak NG 1.52.0, tiny probes, then tests and the qualifier; a private copy of the data reached through a wrapper that only sets
  `ESPEAK_DATA_PATH`; the installation is never modified): on the genuine layout `-v<name>` and `-v<identifier>` give the same PCM for all three voices. In
  the private copy a top-level `lang/<name>` (all three), and a higher-scored *Other Languages* voice (`fr-fr`, `en-gb`), redirected the old `-v<name>`
  command to another sound, while the adaptor stayed PCM-identical to the genuine `-v<identifier>` control; the old adaptor failed those tests before the change and passes
  now. A `lang/fr-fr/voices/fr-fr` tree made the old name command crash natively and did not affect the identifier. A `voices/roa/fr` file is read by the
  native program before `lang/roa/fr`, so the adaptor refuses it before any synthesis. Results are compared by PCM bytes, not by exit codes.
* Documentation corrected: French and Spanish have `fr_dict` and `es_dict` as the primary dictionary with the English dictionary as an additional fallback (not "never
  English"), and the 160-byte voice-file line cap is a conservative adaptor policy below the 190-byte minimum native buffer, not the native limit.
* Limits: the trusted native program and its data are assumed; no filesystem race protection, no closure over every native dependency, no claim that the files are
  the official ones, and nothing about the accent heard. The inspected `language`/`dictionary` attributes are still read from the source, not from probes of
  modified voice files. One runtime, one host.
* Verification after the lookup repair: focused fail-before/after tests, the voice suite, the existing suites, the real-runtime tests and a fresh full native
  qualifier were run serially; counts and logs are kept in the private evidence of this repair.
