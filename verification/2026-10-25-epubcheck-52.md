# EPUBCheck publication check: new adaptor (2026-10-25, allocation 52)

> **Superseded in part (2026-10-25 offline repair).** The launcher environment, network and XML-profile statements, the test counts and the native
> acceptance recorded below describe the first version. The current policy (fixed `JAVA_TOOL_OPTIONS=-Depubcheck.offline=true`, exact DTD catalogue,
> strict UTF-8/UTF-16 profile) and its fresh evidence are in `verification/2026-10-25-epubcheck-52-offline-repair.md`. Receipts and launcher logs from
> before the repair are not compatible with the current launcher text and do not verify.

Scope: the new `epubcheck` adaptor, route `schemaxis.epubcheck/1`, one operation `validate`. It captures one local
`.epub`, preflights the ZIP container on the host, runs the official EPUBCheck with a fixed `--failonwarnings` policy and
publishes `assessment.json` (native report) plus `epubcheck-summary.json` only when the checker reports zero fatal, error and
warning messages. It claims no rendering, device, accessibility or legal certification. No qualification receipt is
registered and `upstream.json` keeps `absorbedVersion` null until shared integration freezes.

## Decision

Product judgement, not demonstrated demand: the Pandoc EPUB publication proves closed package/content consistency of its own
output; a dedicated official standards checker is separate evidence for the same hand-over and strengthens a publishing
handoff more than another export option would. Bounded accordingly: one absolute `.epub`, no authored Java, JAR, profile,
flag, plugin, severity or filter, the default profile and English messages only.

## Native mapping (EPUBCheck 5.4.0)

* Official release v5.4.0, published 2026-09-15, <https://github.com/w3c/epubcheck/releases/tag/v5.4.0>; asset
  `epubcheck-5.4.0.zip` (33093170 bytes) SHA-256 `33350c61038e71dfb3d45a76aed04bf5481e6d5500cb780f6e98db8bbd15a28c`, equal to the
  digest in the GitHub release API record (`https://api.github.com/repos/w3c/epubcheck/releases/latest`). Project documentation:
  <https://www.w3.org/publishing/epubcheck/>. The release record, provenance and `--help` text were retained in the evidence
  directory before mapping; the web pages themselves were not re-fetched by this adaptor work (offline normal admission).
* The distribution is a JAR with a sibling `lib/`, so the adaptor takes a **configured fixed launcher** (`--epubcheck`,
  `schemaxis configure epubcheck`, `SCHEMAXIS_EPUBCHECK`; never PATH, never a receipt). The tested launcher is a private
  two-line shell script (`exec /usr/bin/java -Xmx256m -XX:ActiveProcessorCount=2 -jar epubcheck.jar "$@"`, launcher SHA-256
  `a30cb1a79493d8051a5d0cb7ff3da965b6b2524080a892b36fee79615499d439`, JAR SHA-256
  `2146665a124998dc6c908010ffe0d09dc4f4c8014f2c8fd6a1aa11f64c40ac93`, existing OpenJDK 25.0.4.1). Nothing was installed globally.
* Fixed invocation: `<launcher> captured.epub --json assessment.json --failonwarnings --quiet --maxOfEachMessage unlimited
  --locale en`, plus `--version`. Observed, from direct probes: exit 0 for valid, exit 1 for any fatal/error and, under
  `--failonwarnings`, warning (exit 0 for a warning-only book without the flag); `checker.path` is `./<argument>`, so the fixed
  working directory and file name make it deterministic; messages equal the counters when nothing is truncated. Launcher
  environment was `LANG`/`LC_ALL` only (now also the fixed offline property, see the repair note); the host launcher script limits CPU affinity to two CPUs, CPU time (380 s), output size
  (8 MiB) and open files.
* Network behaviour (first version): the loopback canary (a listening socket, remote image/audio/script/stylesheet references) saw zero
  connections; remote resources are reported as OPF-014/RSC-006 findings. The later source audit found an upstream online fallback for unknown
  EPUB 2 external DTDs that this canary did not exercise; the repair note records the fix and its controls.
* Not mapped: `--profile`, `--mode`, `--customMessages`, `--usage`, `--out`, `--xmp`, expanded EPUB input.

## Limitations and skipped coverage

* One platform (Linux x86-64), one Java (OpenJDK 25), one EPUBCheck release (5.4.0), serial only. No Windows/macOS, no other release, no
  non-default profile, no expanded EPUB, no reading-system, accessibility or legal check, no MPI.
* Correction: the machine has 20 CPUs (see the repair note). The logged `Cpus_allowed_list` (0-1) is the two-CPU cap acting in the native process, not a two-CPU machine; the logging wrapper's
  `/proc/<pid>/limits` grep did not match, so resource limits are asserted only by the launcher text in host tests, not observed natively.
  Memory is bounded by the trusted launcher's `-Xmx`, not by Schemaxis.
* The ZIP preflight is a conservative host policy (for example any entity declaration is refused); the checker is not asked to judge those
  inputs. Zero findings is a scoped result of 5.4.0. The captured copy is writable and unauthenticated.
* `absorbedVersion` stays null; the source-bound qualification record is pending until shared integration (`qualification.json` not written).
